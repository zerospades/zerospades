# ZeroSpades Android port: final research synthesis

Research date: 2026-11-06. Local baseline: commit `8ca45f4cc3418b90afb0fe2ee60fc83775b8eccc` plus the existing uncommitted Android preview/scaffolding. Reference revisions: ySpadesMobile `81e0637c0ba090fcd3a7614a6e9c4a722b5b6fce`; KyroSpades `b380ae85474d37e5a4eee0071894e5398ddb6253`. Two independently supplied reports were also reviewed. This document records the research-only phase; implementation is a later phase.

## Decision and confidence

The strongest path is to **preserve the current ZeroSpades engine**, introduce an Android-only build/platform layer, and adapt its renderer to GLES using ySpadesMobile as a narrowly reviewed reference. KyroSpades supplies useful Android build/platform ideas, but is a different C engine. Both external reports provide useful test ideas, but neither is safe to implement as written. Start with a working, testable native build and renderer before connecting the full mobile HUD.

For HUD architecture, the leading candidate is **native gameplay drawing/input plus Android text UI where useful**, because the engine already renders the minimap efficiently (`Sources/Client/MapView.cpp`, `Sources/Draw/OpenGL/GLFlatMapRenderer.cpp`). However, keep the existing Android HUD as a useful layout/reference and conduct an integration spike before committing to a design. A well-designed Java overlay may be viable; neither external report's absolute performance claims have measurements. In any design, there must be one input owner per interaction and touch menus must remain usable.

This is confidence in a **direction**, not evidence of a playable port or verified device compatibility. The current Android artifact remains a launcher and sample HUD. No native Android game has been compiled or run here.

## Verified code findings

### Build and dependencies

- Root `CMakeLists.txt` currently searches desktop OpenGL and GLEW; `Sources/CMakeLists.txt` builds an executable and includes desktop Unix link assumptions. Android needs a conditional shared-library target, GLES/EGL, NDK system libraries, and consistent builds of actual dependencies. Changing the linker name alone cannot port GL. The shared library does **not** have to be named `libmain.so` if the SDLActivity subclass explicitly loads the actual name and entry point; the version-matched SDL2 Java/native contract must be checked.
- Dependencies include SDL2, SDL2_image, OpenAL Soft, curl/TLS, FreeType, Ogg, Opus/Opusfile and zlib; the current tree already contains ENet and AngelScript sources. Do not replace the bundled network implementation with a different reference engine's dependencies without a reason. Build all selected dependencies for each target ABI, control static/shared PIC and STL compatibility, and inspect final shared library dependencies and exports. Use pinned verified source revisions/toolchain versions, not a moving package repository.
- **Likely ARM64 blocker:** `Sources/AngelScript/projects/cmake/CMakeLists.txt` adds the 32-bit ARM call files for all Android targets, whereas `source/as_config.h` selects `AS_ARM64` on Android AArch64 and the ARM64 C++/assembly sources are not added by the Android branch. Add ABI-specific build sources in a later change and exercise actual script/native calls. This conclusion is based on source, not an NDK build. `AS_MAX_PORTABILITY` is a compile-time configuration and also requires compatible generic bindings; it cannot be dynamically turned on by a runtime test as one report proposes. [AngelScript generic convention](https://angelcode.com/angelscript/sdk/docs/manual/doc_generic.html).
- Android's [16 KB guidance](https://developer.android.com/guide/practices/page-sizes) says NDK r28+ defaults to 16 KB ELF alignment; r27 and lower need the documented flags/configuration. AGP packaging alignment is a separate requirement from ELF alignment. Inspect **every packaged .so**, APK/bundle packaging, page-size assumptions and runtime behavior on both 4 KB and 16 KB devices. AGP/NDK versions alone cannot fix an incompatible prebuilt library. Current preview uses AGP 8.7.3, Gradle 8.9, compile/target SDK 35 and has no native engine.
- GitHub APK distribution is the current requested release channel. If Google Play is added later, [Google's current policy](https://developer.android.com/google/play/requirements/target-sdk) says new apps and updates generally need target API 36 from 2026-08-31, with listed form-factor exceptions; API 35 in the reports is not an adequate universal Play-policy claim. Verify current requirements again at actual publication time.

### GLES and shaders

- `Sources/Draw/OpenGL/GLProgramManager.cpp` builds programs from multiple shader objects of the same stage, including `*shadow*` and `*dlight*` components. OpenGL ES disallows attaching multiple shader objects of the same type to one program ([GLES 3 `glAttachShader`](https://docs.gl/es3/glAttachShader)). A correct Android shader path must assemble or otherwise produce one object per stage while preserving dependencies, macro ordering and settings.
- The current checkout's shader files use legacy constructs including `attribute`, `varying`, `texture2D` and `gl_FragColor`. A search found no literal `#version` directives under `Resources/Shaders/OpenGL`; the first external report's categorical claim that these files contain `#version 120/130` is not supported by this check. Android GLSL conversion requires actual per-program audits, not global string replacement. GLSL ES 3.00 uses an appropriate explicit `#version 300 es` and permits default precision declarations rather than requiring a qualifier on every variable ([Khronos specification](https://registry.khronos.org/OpenGL/specs/es/3.0/GLSL_ES_Specification_3.00.pdf)). Version, directives, extensions, sampler types, output declarations, function compatibility and conditionals all need testing.
- ySpadesMobile combines components and includes GLES-specific device code. Its `glMapBufferRange` mapping uses `GL_MAP_WRITE_BIT`; the first report's proposed `GL_MAP_WRITE_BUFFER_BIT` is not the GLES token. Access flags must reflect each operation; a blanket write/invalidate conversion is not safe for reads or read/write mappings.
- The first report claims ySpadesMobile disables all occlusion queries and that the resulting impact on terrain and performance is severe. Source does **not** establish that: it skips `TimeElapsed` query begin/end on Android, still calls the samples-passed query path, and makes conditional rendering no-op. In the inspected code, conditional rendering surrounds the mirrored water scene (`GLRenderer.cpp`), so it could cause unnecessary reflection work. Actual impact and correctness are unmeasured. Its profiler can still ask for timer query results, so disabled GPU timing needs explicit caller-side handling.
- The second report describes a ySpadesMobile `gl_renderer.c` that skips `glReadPixels`; no such file was found in the examined checkout and its `Sources/Gui/SDLGLDevice.cpp` contains a `glReadPixels` call. Do not rely on that specific allegation. Assess each real readback path and supported formats instead.
- Both reports contain speculative rendering code and performance conclusions. Start with GLES context and minimal drawing, capture shader compile/link logs and FBO completeness, then test real terrain, models, water, effects and presets on multiple drivers. The software renderer is neither proven viable nor proven unusable on mobile until the Android display path and real-device performance have been tested.

### Input, lifecycle and chat

- The ySpadesMobile HUD emits `LButton`, `RButton`, `Up`, etc. Its `Client::CheckKey` compares with configured bindings; defaults include `LeftMouseButton`, `RightMouseButton`, `w`, `a`, `s`, `d` and `Shift`. The mismatch is an objectively identifiable default-binding risk; actual device behavior was not tested. Respect custom bindings or use well-defined engine actions; don't hardcode either set.
- In the current `Sources/Gui/SDLRunner.cpp`, inside `case SDL_WINDOWEVENT`, focus checks use `event.window.type` rather than the window subevent field `event.window.event`. The window-event type and focus subevent are different fields. This is an apparent existing focus-handling defect by source inspection and merits a regression test and fix during implementation, not a claim of on-device validation. See [SDL2 window-event structure](https://wiki.libsdl.org/SDL2/SDL_WindowEvent).
- The current Java HUD has pointer ownership and first-press/last-release behavior; the inactive native bridge queues commands to the game thread. It still needs robust menu transitions and lifecycle integration: `Client::KeyEvent` forwards events to `scriptedUI` when that UI owns input, so a late release may not reach gameplay state. Reset gameplay-owned actions on the correct thread and at the correct transition; test mixed physical/touch input, cancellation, overflow and simultaneous fire. Do not accidentally clear physical inputs held by another device.
- If using SDL finger events, [SDL2's event](https://wiki.libsdl.org/SDL2/SDL_TouchFingerEvent) identifies `touchId` and `fingerId`; the second report's `event.which` is not a member of `SDL_TouchFingerEvent`. Android MotionEvent IDs, SDL touch IDs and SDL finger IDs are different domains; do not mix them or dispatch the same finger through independent Java and SDL paths. Choose explicit synthetic touch/mouse behavior for gameplay **and** menus/external mice.
- Native `ClientChatWindow` already calls `ClientUIHelper::SayGlobal/SayTeam` → `ClientUI::SendChat` → `NetClient::SendChat`; incoming messages are recorded by existing client handlers. Preserve command, channel, encoding, filtering and error behavior when integrating an Android chat overlay. JNI `GetStringUTFChars` uses **modified UTF-8**, not arbitrary standard UTF-8; use a deliberate UTF-16/UTF-8 conversion or Java byte array and test supplementary Unicode, embedded NUL, composition and server byte limits ([Android JNI guidance](https://developer.android.com/ndk/guides/jni-tips)). Do not bypass the engine by directly emitting raw packets just because an external report suggests it.
- SDL2 documents blocking pause and attempted GL context restoration, but context recovery can fail ([SDL2 Android guide](https://wiki.libsdl.org/SDL2/README-android)). The second report's asserted lifecycle callback names and automatic native thread restart are not established for our chosen SDL2 build. Handle surface/context lifetime for this renderer explicitly; test normal resume, context loss, process recreation, keyboard, audio interruptions and safe areas. Reset events documented for SDL's renderer are not automatically sufficient for this custom renderer.

### Grenade, HUD and timer

- `Client::SetSelectedTool`, `ClientPlayer::IsChangingTool`, `Client::CanLocalPlayerUseTool`, `Client::UpdateLocalPlayer`, `Player::SetWeaponInput`, and `Client::PlayerThrewGrenade` define the actual sequence. A quick throw must wait until grenade tool is ready and its press has been observed in a game update; then release and observe throw/network processing before any optional tool restoration. Handle sprint, cooldown, ammo, death, disconnect, focus cancellation, and a user selecting a different tool. The first report's immediate press after selecting grenade and fixed restoration delay do not implement those guarantees.
- The first report's lock-free two-buffer sample is unsafe: a writer can reuse a buffer while the reader is still copying it; atomic buffer indices do not make the non-atomic struct data race-free. Start with a small mutex-protected owned snapshot or immutable ownership, and profile before replacing it with a correctly proven lock-free mechanism. For native HUD rendering on the game thread, no cross-thread snapshot is needed for that data.
- `ScoreboardView.cpp` derives CTF scores/capture limit from `CTFGameMode` and TC scores by counting owned territories against total territories. **User clarification:** both bars must show each team's current score as a fraction of the shared game-mode maximum, not the larger current score. The preview uses this denominator. With an unknown or non-positive maximum it renders empty bars; the live game-mode data still needs integration and testing.
- `NetClient.cpp` enters `NetClientStatusConnected` after map transfer, but it also re-enters map-receiving status during map changes on the same server and later becomes connected again. A join timer must survive a map transition on the same connection and reset on actual disconnect/reconnect or server change, rather than resetting at every `SetWorld` or every return to connected. Define the successful first-join boundary and sleep behavior, then verify with a server.
- `Player` and `Weapon` expose health, tool, blocks, grenades, magazine ammo and stock. Existing minimap, score and killfeed rendering should be adapted without suppressing unrelated feedback. Keep at most five kill entries, accurate icons and colors; no flags and no prohibited button. Nearly full-screen chat must use 80%-opaque background.

### Assets and networking

- `android/tools/package_resources.py` creates five local paks; the essential external `pak000-Nonfree.pak` and `font-unifont.pak` plus their license texts are still needed for a complete game. Structure/ZIP validation is not source authentication; establish trustworthy, pinned hashes and review exact bundled notices.
- The [r33 nonfree license](https://github.com/yvt/openspades-paks/blob/r33/Nonfree/LICENSE.md) permits specified forms of distribution for OpenSpades or qualifying derived free-download, free-of-charge non-commercial open-source projects, requires the notice, and prohibits separately redistributing the audio files. The repo's `Resources/PakLocation.txt` is more conservative about separately distributing the pak. Neither report's claim that all public redistribution is prohibited is supported by the complete license. Whether this project/release qualifies and how to reconcile the notices requires careful review; no automatic check is a legal determination. Prefer official-source fetch only if authorized; otherwise use permitted private/user-supplied assets. Fail clearly if required files are missing.
- Existing `GameAssetsInstaller` is preparatory, unused, and updates individual files atomically rather than the full set as a transaction; an interrupted update can leave versions mixed. Authenticate assets, stage a complete version, activate only when validated, and test process death/disk-full recovery.
- `NetClient.cpp` receives map chunks over ENet; the first report's blanket assertion that map downloads are native libcurl HTTP transfers is incorrect for this path. `MainScreenHelper.cpp` uses curl for server lists, whose primary default is currently **HTTP** and fallback **HTTPS**. Game UDP and HTTP(S) are separate risks. Verify the specific endpoints and certificate validation; decide whether to prefer an available HTTPS endpoint without breaking compatibility. Android Network Security Config does not automatically prove the independently built libcurl TLS backend follows its policy. Never turn off certificate or hostname verification, and don't introduce certificate pinning without an operational rotation plan.

## Recommended sequence and gates

1. **ABI/toolchain spike:** Pin a coherent SDL2 Java/native pair and Android toolchain; correct AngelScript ABI-specific build; build and execute a small native script-binding test for arm64-v8a and, when feasible, x86_64. Check `.so` dependencies, `SDL_main`, ELF and APK 16 KB alignment. Gate: clean build and executable tests, not merely a successful CMake configure.
2. **Platform bootstrap and assets:** Integrate settings launcher, asynchronous complete-asset installation and SDLActivity. Define settings precedence with the native `Settings::Load()` and persistent in-game settings. Gate: fresh install and restart show actionable failures when dependencies/assets are missing; no false playable release.
3. **Minimal GLES then engine rendering:** GLES context → simple geometry → engine shaders → terrain/models → actual water/effects. Track feature support explicitly, capture compiler/linker/FBO errors, and test representative settings on physical GPU vendors. Gate: no silent degraded/invalid rendering.
4. **Join and game actions:** Server browser/direct connect, map download, team/weapon selection, spawning, stable gameplay and audio. Integrate one input owner and thread-safe reset, then frame-aware grenade state. Gate: real multiplayer controls, including simultaneous touch and focus transitions.
5. **Requested HUD and real chat:** Use native existing minimap/state/event sources where appropriate, Android IME where beneficial, preserve all requested positions and semantics, no duplicate HUD or forbidden control. Gate: real state, actual send/receive, Unicode, safe areas, timers and max-five killfeed.
6. **Performance/release:** Profile before/after frame-time distributions, memory, startup, thermal behavior and input latency on low/mid/high devices over sustained sessions. Add meaningful emulator checks and physical-device test matrix. Release only a fully validated signed game; keep debug artifacts clearly labeled as previews and never silently fall back to debug signing for production.
