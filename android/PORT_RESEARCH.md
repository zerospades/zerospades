# ZeroSpades Android port: research and validation plan

Research date: 2026-11-06. This is a design investigation, not a claim that the Android port is finished. The checked-in Android app remains a launcher and HUD **preview**, not a playable game. No implementation changes were made for this research pass.

## Evidence and conclusions

### Starting point

The game in this repository is the required C++ ZeroSpades codebase. Its desktop build targets an executable and relies on desktop OpenGL/GLEW and platform-specific libraries. `Sources/Gui/SDLRunner.cpp` owns the SDL event/game loop; `Sources/Gui/SDLGLDevice.cpp`, `Sources/Draw/OpenGL/` and `Resources/Shaders/OpenGL/` implement the renderer. Simply linking against GLES does not provide desktop-only GL entry points or make desktop shaders portable. ZeroSpades has a software renderer too, but its Android presentation, performance, and feature parity have not been demonstrated.

The existing Android Java HUD, native input router, asset packaging script and filesystem preparation are partial scaffolding. There is no Android SDL game activity, native game shared library, actual HUD state feed, native chat send/receive, or quick-grenade implementation. Android preferences are not yet applied to engine settings. Host unit tests and stub-based Java compilation are not an Android APK build or device test.

### A closely related Android reference

[ySpadesMobile](https://github.com/uamo11/ySpadesMobile) at commit [`81e0637c0ba090fcd3a7614a6e9c4a722b5b6fce`](https://github.com/uamo11/ySpadesMobile/tree/81e0637c0ba090fcd3a7614a6e9c4a722b5b6fce) is substantially closer to this codebase than KyroSpades: it has recognizably related `Sources/Client`, `Sources/Gui`, `Sources/Draw/OpenGL` and asset layouts. GitHub describes it as a ySpades mobile port; its repository is not marked as a GitHub fork. The precise history and compatibility with our current game behavior still need investigation. KyroSpades, at `b380ae85474d37e5a4eee0071894e5398ddb6253`, is a different C engine and remains useful only as a platform reference.

Specific observations from source and GitHub Actions, not claims of successful gameplay:

- Its [CMake](https://github.com/uamo11/ySpadesMobile/blob/81e0637c0ba090fcd3a7614a6e9c4a722b5b6fce/Sources/CMakeLists.txt) builds an Android shared library and links GLESv3/EGL/Android rather than GLEW/X11. The [Gradle configuration](https://github.com/uamo11/ySpadesMobile/blob/81e0637c0ba090fcd3a7614a6e9c4a722b5b6fce/android/app/build.gradle) selects arm64-v8a, API 24 minimum, and NDK 26.1. The [activity](https://github.com/uamo11/ySpadesMobile/blob/81e0637c0ba090fcd3a7614a6e9c4a722b5b6fce/android/app/src/main/java/org/yspades/ySpadesActivity.java) extends SDLActivity and starts `SDL_main`. SDL Java and native versions must match; do not mix arbitrary copies.
- Its [SDL GL device](https://github.com/uamo11/ySpadesMobile/blob/81e0637c0ba090fcd3a7614a6e9c4a722b5b6fce/Sources/Gui/SDLGLDevice.cpp) contains explicit GLES changes, including replacement of `glMapBuffer` with `glMapBufferRange` and omission of desktop-only operations. Some features such as conditional rendering and time queries are disabled or altered on Android; their callers and visual/performance consequences require review.
- Its [shader manager](https://github.com/uamo11/ySpadesMobile/blob/81e0637c0ba090fcd3a7614a6e9c4a722b5b6fce/Sources/Draw/OpenGL/GLProgramManager.cpp) concatenates shader components and adds GLES precision/extension text. It deduplicates declarations by a simple line/name heuristic. That does not prove equivalence across preprocessor branches, permutations or GPU drivers. A local comparison found changes in 20 renderer files (346 insertions, 190 deletions) and five shader files, in addition to broader game differences. Treat these as a map of likely work, not a safe patch to apply wholesale.
- Its HUD is implemented in native C++ and receives SDL finger events. That is an alternative to the existing Java overlay; mixing both input systems without explicit ownership risks duplicate actions. Its [touch implementation](https://github.com/uamo11/ySpadesMobile/blob/81e0637c0ba090fcd3a7614a6e9c4a722b5b6fce/Sources/Client/TouchHUD.cpp) does not match the requested layout. More importantly, it sends `LButton`, `RButton`, `Up`, `Down`, `Left`, `Right`, and `LeftShift` to `Client::KeyEvent`, whereas its own default bindings are `LeftMouseButton`, `RightMouseButton`, `w`, `s`, `a`, `d`, and `Shift`. Its `CheckKey` compares names case-insensitively but does not generally translate those aliases. Under those defaults these touch actions appear mismatched; runtime behavior has not been tested. Do not use that input mapping as proof of playability.
- Its [Android CI run](https://github.com/uamo11/ySpadesMobile/actions/runs/42127145635) for the examined commit reports success through Gradle build, artifact upload and release upload. This proves only the reported build workflow completed. The asset preparation commands swallow errors (`|| true`), and the separate [emulator run](https://github.com/uamo11/ySpadesMobile/actions/runs/42127642924) was cancelled. The emulator workflow takes a screenshot but contains no gameplay assertions. No successful emulator test in the latest 50 listed emulator runs was observed at the time of checking. Neither these results nor the README establish playable networking, rendering or input.
- The repository includes a tracked APK. Inspection of that tracked file showed seven paks and two arm64 shared libraries. Its relationship to the exact examined source/build is unverified; it is not a license determination or proof the current release contains the correct assets. Do not copy this binary or its assets into our tree.
- Its repository license file is GPLv3; individual files, bundled libraries and resources may carry other terms. Preserve attribution, notices, corresponding source and any applicable license obligations if code is adapted. Check the provenance of each borrowed change. Legal conclusions and nonfree asset distribution need appropriate review.

### Platform facts and limits

- The [SDL2 Android guide](https://wiki.libsdl.org/SDL2/README-android) describes SDLActivity/native integration and pause/resume behavior. SDL attempts to restore the GL context, but restoration can fail. This engine uses its own GL renderer, so SDL renderer reset guidance alone does not prove that all of our own GL resources will be recreated correctly. Define and test explicit recovery or safe restart.
- The [Android insets guide](https://developer.android.com/develop/ui/views/layout/edge-to-edge) requires careful handling of system bars, cutouts and gesture insets, particularly for target SDK 35+ on Android 15+. Landscape safe areas, IME and coordinate conversion need real-device tests; fixed pixel offsets are not a reliable substitute.
- Android's [16 KB page-size guidance](https://developer.android.com/guide/practices/page-sizes) recommends AGP 8.5.1+ and NDK r28+ with compatible dependencies, while also testing runtime assumptions. Verify every packaged native library's ELF alignment, APK alignment and execution on a 16 KB environment. This matters for compatibility even if GitHub APK distribution, rather than Google Play, is the immediate goal. Recheck current Play policies if Play publication is requested.
- SDL can synthesize mouse events from touches ([SDL2 documentation](https://wiki.libsdl.org/SDL2/README-android)); choose and test explicit synthetic-event policies for gameplay and menus, including real external mice. IME text composition, cancellation and lifecycle vary by version and must be tested with the chosen SDL2 version.
- Android recommends measuring frame pacing, CPU/GPU load and thermal sustainability rather than guessing: [performance guidance](https://developer.android.com/games/optimize/overview), [slow sessions / Swappy](https://developer.android.com/topic/performance/issues/slow-session). Swappy or thermal adaptation is a later measured option, not a prerequisite or automatic performance fix. An emulator can use host or software graphics; it is not a substitute for mobile GPU testing ([Android emulator graphics](https://developer.android.com/studio/run/emulator-acceleration)).
- The game needs `pak000-Nonfree.pak` and `font-unifont.pak` as well as local paks; see `Resources/PakLocation.txt`. The local notice limits redistribution of the nonfree pak separately from releases or compiled binaries; review the full upstream license and intended distribution before bundling. Do not assume all assets inherit the code license. Verify licenses/notices for every dependency and asset.
- UDP gameplay and HTTP(S) server discovery are distinct paths. Test DNS, internet permissions, discovery and direct server joins; validate TLS and hostname verification with the actual libcurl TLS backend and CA store. Android's [network security configuration](https://developer.android.com/privacy-and-security/security-config) is not proof that a native networking library automatically enforces the same policy. Never disable certificate verification as a shortcut.

## Proposed implementation architecture (hypotheses, not yet validated)

1. **Build reproducibly first:** retain this repository's game sources and add an Android-only CMake shared-library target. Pin compatible SDL2 Java/native source, NDK, Gradle/AGP and dependency revisions. Cross-compile SDL2, SDL2_image, OpenAL, curl/TLS, FreeType, Ogg/Opus/Opusfile, compression and existing embedded components consistently per ABI. Explicitly check AngelScript's Android/ARM64 calling convention and scripting at runtime. Avoid using a moving vcpkg checkout or masking missing assets as a successful build. Initially target arm64-v8a; add x86_64 for practical emulator CI if dependencies permit. Verify dynamic library dependencies and `SDL_main` export.
2. **Integrate SDL lifecycle:** keep the requested settings launcher; install validated assets off the UI thread, translate stored settings into actual native settings before renderer/client initialization, and launch a matching SDLActivity. Account for failure, updates, process recreation, back, rotation, focus, audio interruption and surface/context loss. Do not claim launcher settings work until verified in-engine.
3. **Prove GLES rendering incrementally:** audit ySpadesMobile patches one by one against current ZeroSpades, isolate Android-specific behavior and avoid overriding game features. Explicitly handle GLES capabilities, formats, framebuffer completeness, extensions and shader versions/precision; compile/link and exercise every reachable shader permutation on multiple drivers, checking logs. Decide degraded effects based on correctness and measurements, not silent no-ops. Test software renderer only as a fallback if it is actually usable and performant.
4. **One input owner per mode:** decide between the existing Android overlay and native SDL touch HUD after a small integration spike. Do not run both simultaneously. In game, adapt commands to actual binding/action semantics on the game thread; in menus, deliver absolute pointer or proper UI events. Ensure same-button multi-finger reference counting, cancellation, overlapping pointers, focus loss and held-key releases. Bound/coalesce motion without dropping required press/release transitions. Ensure input remains correct with custom keys and ADS hold/toggle. Implement grenade selection, cook/release and previous-tool restoration as a real state machine respecting frames, cooldowns, ammo and death.
5. **Live HUD and chat:** publish immutable game-thread snapshots/events at a controlled rate to the selected HUD, including real minimap/markers, health, tool and counts, current scores and maximum, join timestamp, and last five kill messages. Avoid allocating/copying a full map every frame; document bitmap ownership and thread safety. Respect the user's screenshot and exclusions: two fire buttons, joystick, ADS, reload, grenade, sprint, crouch, tool cycling, map, crosshair, chat, no team flags or forbidden button. Chat is nearly full screen at 80% background opacity, supports real global/team send and incoming messages, IME composition, close/cancel and reconnect. Suppress/adapt duplicate desktop HUD elements rather than hiding gameplay UI blindly.
6. **Networking and audio:** exercise server list, direct joins, map download, team/weapon selection, spawn, gameplay packets, chat, disconnect and reconnect. Validate audio playback, focus loss/recovery and Bluetooth/device routing. Report missing assets and connectivity errors clearly.
7. **Measure then optimize:** establish repeatable scenes, settings, device/OS/GPU matrix and 30-minute sustained tests. Record frame-time distribution (median and p95/p99), 1% lows, load time, memory, thermal state, battery and crashes. Profile CPU/GPU and minimize overdraw, readbacks, synchronization, allocations and excessive texture uploads. Consider resolution/effects tiers and frame pacing only after bottlenecks are identified, and compare image correctness and input latency before/after. No performance targets can honestly be guaranteed without device data.
8. **CI and release:** build debug APK and tests from clean pinned inputs; verify asset completeness, licenses, architectures, page alignment and symbol/dependency integrity; add emulator smoke tests with meaningful assertions and log capture, then physical-device multiplayer tests. Keep preview/prerelease naming until acceptance criteria pass. A public stable APK requires a persistent secure release-signing key and a documented license-compliant asset strategy; do not silently publish debug-signed builds as production.

## Acceptance test matrix

- Fresh install, upgrade with saved settings, missing/corrupt assets, offline launch and process recreation.
- GLES initialization and all enabled graphics presets, maps, models, water/shadows/effects and error paths; 4 KB and 16 KB pages. Exercise two or more physical GPU vendors, representative low/mid/high devices and Android versions; test display cutouts, gesture and three-button navigation, multiple aspect ratios and rotation.
- Server browser/direct join, successful map load, team and weapon select, spawn, move/turn/ADS, both fire buttons, reload, block/spade, grenade, sprint/crouch and correct ammo/health/score/timer/killfeed. Simultaneous movement, looking and firing; custom key bindings; cancel/pause while holding actions.
- Real chat send/receive in both channels, Unicode/IME composing, keyboard close, focus regain and disconnect. Correct HUD updates and no duplicated desktop UI; correct minimap orientation/markers and screenshot placements.
- Repeated background/foreground, lock screen, interruption, audio focus changes, resize/surface loss, network interruption and reconnect; verify no stuck actions, leaks or crashes.
- Sustained thermal/frame-time tests and before/after traces. Test a real server and at least two actual Android phones; emulator-only results are insufficient.

## Open questions / decisions before declaring confidence

- Which Android device models, OS versions and GPUs can be tested, and what minimum OS and 32-bit support does the user need? The initial arm64-only proposal is not a guarantee of universal support.
- Which server(s) can be used for multiplayer validation? Is server discovery required alongside direct join? Test with permission and avoid production disruption.
- Where will legally distributable external assets come from in CI? Confirm license terms, availability and verification (hash/version), and avoid embedding secret credentials.
- Exact scope of graphics fidelity versus mobile defaults; objective frame-time and thermal targets need hardware and user agreement.
- Verify the current launcher values' exact native setting formats and precedence. Decide whether activity overlay or renderer-native HUD gives the cleanest, best-tested input/UI integration after the SDL build exists.
- An Android SDK/NDK, Gradle distribution and emulator are not available in the present sandbox, and external network access is restricted. GitHub Actions may provide build infrastructure, but no run for this port has yet proven a native Android build. Physical-device verification requires user or external test access.
