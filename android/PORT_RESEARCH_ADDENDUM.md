# ZeroSpades Android research: implementation-focused addendum

Date: 2026-11-06. This supplements `PORT_RESEARCH.md`. The findings below come from source inspection, not an Android build or runtime test. No gameplay implementation was added during this research pass. The Android launcher and HUD are still only a preview.

## 1. Concrete native build blocker: AngelScript on Android ARM64

The bundled `Sources/AngelScript/include/angelscript.h` reports version 2.38.0. In `Sources/AngelScript/source/as_config.h`, Android AArch64 selects `AS_ARM64`, while Android x86_64 selects `AS_X64_GCC`.

However, the Android branch in `Sources/AngelScript/projects/cmake/CMakeLists.txt` adds only `as_callfunc_arm.cpp` and `as_callfunc_arm_gcc.S` for **every** Android ABI. Those files are guarded for 32-bit ARM; the existing Linux ARM64 branch is explicitly `NOT ANDROID`. It does not add `as_callfunc_arm64.cpp` and `as_callfunc_arm64_gcc.S` for Android. `as_callfunc.cpp` calls `CallSystemFunctionNative` on ARM64, and the ARM64 implementation and assembly helpers are in the omitted files. This is a strong static indication of an ARM64 link/runtime build blocker; the precise failure is not confirmed without an NDK build.

Implementation direction: branch on the **target ABI**, add the correct ARM64 C++ and AArch64 assembler files only for arm64-v8a and 32-bit ARM sources only for armeabi-v7a, and check x86_64 independently. Keep architecture-specific assembly out of other builds. Test `asGetLibraryOptions`, function/method registration, by-value structs, exceptions and real game scripts on every supported ABI. Simply defining `AS_MAX_PORTABILITY` is not automatically a solution: [AngelScript documents](https://angelcode.com/angelscript/sdk/docs/manual/doc_generic.html) that this mode requires the generic calling convention. Its [changelog](https://www.angelcode.com/angelscript/sdk/docs/articles/changes2.html) records Android ARM64 native convention support beginning with 2.35.1, but that does not prove this project's build and script bindings work.

## 2. Why shader linking needs real redesign, not just GLES headers

ZeroSpades `Sources/Draw/OpenGL/GLProgramManager.cpp::CreateProgram` attaches multiple separately compiled shader components, including components returned by shadow/dynamic-light helpers. Desktop OpenGL permits attaching multiple shader objects of the same type; OpenGL ES does not: a second shader of the same type causes `GL_INVALID_OPERATION` ([OpenGL ES 3 reference](https://docs.gl/es3/glAttachShader), [desktop GL comparison](https://docs.gl/gl3/glAttachShader)). So a direct GLES compile/link port will fail for affected shader programs even after unsupported C++ GL calls are replaced.

The repository contains 47 `.program`, 63 `.fs` and 57 `.vs` files under `Resources/Shaders/OpenGL` in this checkout; this count does not determine how many permutations are reachable. ySpadesMobile combines source components per stage, which illustrates a possible direction. Its line-based declaration deduplication is not, by itself, a correctness proof.

Implementation direction: on Android, collect ordered shader components for each program/stage, expand the same shadow and light selections and settings, assemble one legal source per stage with explicit language version, extension directives, defines, precision and source mapping, then attach one compiled object per stage. Resolve duplicate declarations deliberately with tests—not by stripping all lines sharing an identifier without regard to conditional compilation or type. Preserve desktop behavior by isolating Android changes. Verify GLSL ES compatibility for every enabled combination and log full source/program names plus compile/link errors. Basic rendering, screenshots and reference comparisons should precede optimizing shader caching. Geometry shaders and advanced features require explicit capability decisions, not silent fallbacks.

## 3. Existing game-state sources for the HUD

All game-state access below should occur on the owning game thread. For an Android-view overlay, use owned immutable snapshots/events with a clearly defined lifetime; do not expose raw `World`/`Player` pointers across threads. Native in-engine drawing can often avoid a Java snapshot for graphics and minimap. Neither architecture has yet been benchmarked or fully integrated.

- `World::GetLocalPlayer()` and `Client::GetWorld()` provide nullable/optional access, important during connection, respawn, spectating and disconnect. `Player.h` exposes `GetHealth`, `GetTool`, `GetWeaponType`, `GetNumBlocks` and `GetNumGrenades`; `Weapon.h` exposes `GetAmmo` and `GetStock`. `Client_Draw.cpp` already distinguishes weapon ammo from blocks and grenades. Health display also uses `Client::lastHealth` in some UI paths; verify which value is intended during damage/respawn animation.
- `ScoreboardView.cpp::GetTeamScore` and `GetCaptureLimit` show mode-specific semantics: CTF uses each team's score and capture limit; TC counts territories owned by each team and uses total territories as the maximum. Preserve neutral territory handling and deal explicitly with missing/zero maximum or unknown modes. The numbers shown are current scores; the bar denominator is the applicable mode maximum, subject to the user's intended UI behavior. Avoid assuming all modes expose CTF score fields.
- `MapView.cpp::Draw` already renders the minimap and markers through `IRenderer::DrawFlatGameMap`. `GLFlatMapRenderer` builds a map texture, marks chunks dirty when blocks change, and uploads only dirty chunks. Reusing or adapting this native path could avoid a full GPU readback and Java bitmap transfer every frame; retain rotation, zoom, marker visibility and update behavior. This is an architectural reason to prototype native map/HUD rendering, not proof that a hybrid overlay is too slow.
- `Client_Update.cpp` creates formatted killfeed entries and adds them to `killfeedWindow`. Entries can include team colors, kill icons, distance and streaks. A five-entry mobile feed should preserve desired information and expiration behavior; blindly passing the internal formatted string to Android TextView may display control markup instead of icons/colors. Either draw/adapt the existing feed with a five-message cap, or define structured events explicitly.
- The join timer needs a well-defined successful join boundary, rather than client construction or preview entry. Locate and validate the transition using real connections, spectating, reconnect and server changes. Choose one monotonic clock domain and document whether elapsed time continues while the device sleeps; do not compare Java and native timestamps without confirming their clock semantics.

## 4. Chat and input: actual source paths and a release risk

The existing in-game chat path is `ClientChatWindow::OnSay` → `ClientUIHelper::SayGlobal/SayTeam` → `ClientUI::SendChat` → `activeNet->SendChat`. `NetClient::SendChat` writes the chat packet; `SendChatUTF8` is a distinct API. Incoming player/server messages are handled in `NetClient.cpp` and recorded/displayed through `Client_NetHandler.cpp` and `ClientUI::RecordChatLog`. Preserve the existing path's encoding and command semantics unless a change is explicitly designed and tested. The SDL runner already forwards `SDL_TEXTINPUT` and `SDL_TEXTEDITING`, and starts/stops text input when the view requests it; that still requires Android keyboard/IME testing.

The current **inactive** Java-to-native touch router queues events to the game thread and uses configured bindings. Its `DrainTouchInput` resets held gameplay actions when the view needs absolute coordinates. There is a subtle hazard: `Client::KeyEvent` routes events to `scriptedUI` first when it needs input. Therefore, if the UI becomes active *before* a held-key release is routed, that release may go to the UI rather than clear the gameplay input. In addition, `Client::UpdateWorld` intentionally keeps movement when text input is active. This is a code-path risk, not a device-verified bug, and host router tests do not prove the complete game behavior.

Implementation direction: make gameplay ownership transition explicit on the game thread, clear the gameplay input state at the correct boundary rather than assuming simulated key-up reaches it, and preserve native physical-input behavior deliberately. Test active movement/fire followed by chat, menu, focus loss and screen lock; verify no movement or fire remains stuck after closing. Handle two simultaneous fire buttons by counting their active sources, and test mixed physical/touch input. Decide separately how menu taps reach native UI and how Android/SDL-generated synthetic mouse events are filtered.

## 5. Grenade quick throw: frame-level constraints

`Client::SetSelectedTool` changes the selected tool and records the last tool. `ClientPlayer::IsChangingTool()` remains true until the raise/lower animation finishes; during the change `CanLocalPlayerUseTool()` rejects weapon input. `ClientPlayer::Update` sends the tool change as its transition advances. `Client::UpdateLocalPlayer` applies accepted input, sends player/weapon input, and can auto-switch away from an unavailable tool. `Player::SetWeaponInput` starts cooking on the primary rising edge and throws on the falling edge; `Client::PlayerThrewGrenade` sends the actual grenade through `activeNet`.

A proposed state machine must therefore wait for the selected grenade and actual tool readiness before issuing a primary-down edge, hold it until the game has observed that edge, then issue a primary-up edge and observe the throw before any optional restoration. Press and release drained within the same update cannot be assumed to generate both edges. Define explicit behavior for a tap versus a held grenade button, cancellation/focus loss while a grenade is cooking, sprint, cooldown, out-of-grenades, death, disconnect, user-initiated tool changes, and restoration when the previous tool is no longer selectable. Do not call `SendGrenade` directly to bypass game rules. Safety and exact cancellation semantics need gameplay tests and user confirmation if behavior is ambiguous.

## 6. Launcher settings and asset installation

- `Settings::Load()` reads `SPConfig.cfg` before the existing `--override-cvar` values in `Sources/Gui/Main.cpp` are applied. Overrides intentionally revert before shutdown and do not persist in native config. They are a possible per-launch bridge, but the launcher needs a single source of truth for persistent settings and careful precedence with in-game changes. A robust design should avoid two settings stores silently overwriting one another.
- The current `GameAssetsInstaller` checks bundled pak presence and hashes installed bytes against incoming bytes, but matching those two hashes does not authenticate the source. It replaces files atomically **one at a time**, not as an all-or-nothing set; interruption or failure can leave a mixture of versions. It copies and syncs each asset before comparing, even when already installed. A future design can use verified version/hash metadata and a staged versioned directory with an atomic activation marker, recovery after interruption, sufficient-space checks, and clear errors. Keep the previous good set until the new one is complete. Validate assumptions on Android filesystems and during process death before calling this atomic in production.
- `android/tools/package_resources.py` validates archive structure and selected entries, not publisher authenticity. Pin the upstream source and expected cryptographic digest from a trusted release process, preserve the exact license texts, and don't disable certificate verification. A failed build or missing external paks must not produce a game release.
- The local `Resources/PakLocation.txt` conservatively asks not to redistribute the nonfree pak separately from OpenSpades releases/compiled binaries. The upstream [r33 Nonfree license text](https://github.com/yvt/openspades-paks/blob/r33/Nonfree/LICENSE.md) is more specific: it permits specified distributions for OpenSpades or qualifying derived free-of-charge, non-commercial open-source projects, including certain separate packages for the sole purpose of providing assets; it prohibits separately redistributing audio files and requires the notice. Read the full exact license and reconcile the local notice and project circumstances; this is not a legal opinion or a guarantee of permission. [r33 Unifont license](https://github.com/yvt/openspades-paks/blob/r33/OfficialMods/LICENSE) identifies GPL terms and a font embedding exception; inspect all relevant conditions.
- GitHub API returned the official r33 release metadata (published 2017-01-05; dev ZIP size 4,036,321 bytes; no API digest recorded). Attempting to download that asset in this sandbox failed because the redirect went to a restricted host. The archive itself was not inspected and no trusted SHA-256 is claimed. The r33 source-tree license files were read through GitHub's API; verify the actual downloaded archive's included license and contents before distributing.

## 7. Prioritized next validation gates

1. Review the two independent reports when received; compare claims against source and official documentation, and resolve contradictions before coding.
2. In a real Android CI environment, demonstrate ABI-specific AngelScript compilation/linking and tiny script execution; ensure tests fail on missing call stubs. Separately establish pinned SDL2/native dependency builds and 16 KB ELF/APK checks.
3. Demonstrate an SDL game activity and correctly initialized native game with verified assets. Capture actionable startup and shader errors; do not publish as playable.
4. Prove correct basic GLES rendering, then enabled shader permutations and in-game scenes on distinct GPU vendors. Benchmark native minimap/HUD versus any proposed Android overlay.
5. Integrate gameplay input and chat with explicit focus ownership and release tests, then live HUD data, grenade sequencing and real multiplayer. Gate production release on physical devices, lifecycle and sustained performance tests.
